# DSL2 网站与计分系统架构

## 总体结构

```text
单一公开 GitHub 仓库 D:\scdoudizhu-dsl2
  data-source：原始记录、别名、积分流水、修正与复核
            │
            │ 确定性汇总 + 网站数据导出 + 契约校验
            ▼
  src/data：面向网站的积分结果
  名次、显示名、总积分、段位、统计时间
            │
            │ Astro 静态构建，只读取 src 与 public
            ▼
GitHub Pages → scdoudizhu.com
```

旧目录不参与构建或部署，只作为只读来源。仓库是否公开与网站是否展示某项数据是两个不同边界：为方便社区赛事开发，原始和内部资料可以进入同一公开仓库，但不得被页面、网站接口或构建产物引用。

## 公开网站技术方向

建议从空项目使用 Astro 静态生成和 TypeScript，但不复制当前 `scdoudizhu-site` 的组件、样式或数据结构。

选择原因：

- 首页、规则、赛程、通知和积分榜本质上适合静态生成。
- 核心内容可以在服务器构建阶段写入 HTML，关闭 JavaScript 仍然可见。
- 能继续使用 GitHub Pages，降低域名切换和长期维护成本。
- 可以只在搜索、筛选等确有价值的位置加入少量客户端脚本，不需要 React 作为默认依赖。
- TypeScript 可同时验证公开数据和内容配置，减少字段漂移。

“另起炉灶”体现在全新的项目历史、信息架构、数据契约、视觉系统和构建边界，而不是为了不同而选择更复杂的部署平台。

具体依赖版本只在初始化实现阶段锁定，并由 lockfile 固定。不得从旧仓库复制 `package.json`、lockfile、`node_modules` 或构建产物。

## 公开数据契约

公开积分导出只允许以下概念：

```json
{
  "schemaVersion": 1,
  "season": "dsl2",
  "exportId": "公开导出编号",
  "standingsAsOf": "ISO 8601 时间",
  "publishedAt": "ISO 8601 时间",
  "entries": [
    {
      "rank": 1,
      "displayName": "公开显示名称",
      "points": 0,
      "tier": "王者"
    }
  ]
}
```

最终契约需要等待同分名次规则确认。在确认前，正式榜单保持空状态，不能通过数组顺序假装已经解决同分问题。

构建时至少验证：

- 根字段和选手字段使用白名单，出现未知字段即失败。
- 赛季标识和契约版本有效。
- 时间使用带时区的 ISO 8601 格式。
- 显示名称非空，并经过长度与控制字符检查。
- 积分为整数且不小于零。
- 名次、段位与已确认规则一致。
- 不存在重复公开显示名；别名冲突应在 `data-source` 的运营资料中解决。
- 文件中不存在禁止字段名称。

## 仓库内运营数据模型

仓库的 `data-source` 与配套脚本至少维护以下实体。它们可以随源码一同提交，但不会直接进入网站：

### 选手与别名

- 稳定内部选手 ID。
- 公开显示名称。
- KK 名称。
- 韩服名称。
- 历史别名。
- 合并和拆分记录。

公开显示名称不能作为内部主键。无报名参赛意味着新名称可能随时出现，必须支持“待确认身份”状态。

### 比赛日

- 比赛日 ID。
- 周次和阶段。
- 日期、时间和时区。
- KK 或韩服。
- 2v6、3v5、战队联赛或 8R。
- 状态及临时通知。

### 对局与参赛记录

- 对局 ID 和所属比赛日。
- 原始证据索引。
- 每名选手的角色和胜方。
- 按规则派生的积分事件。

### 赛事工作

- 工作记录 ID。
- 比赛日、人员和主机/主播/统计职责。
- 对应积分。
- 录入与复核信息。

### 积分事件与修正

所有积分变化使用追加式事件：

- 事件 ID。
- 选手 ID。
- 事件类型。
- 来源记录 ID。
- 分值。
- 规则版本。
- 录入时间和复核时间。

已经发布的错误不直接覆盖原事件，而是追加有理由、有复核人的修正事件。总分始终由事件汇总计算。

## 计分规则配置

规则作为版本化配置保存，不散落在页面组件或脚本常量中：

| 事件 | 分值 |
|---|---:|
| 地主获胜 | +12 |
| 地主失利 | +3 |
| 农民获胜 | +8 |
| 农民失利 | +2 |
| 主机 | +30 |
| 主播 | +30 |
| 统计 | +20 |

每次积分事件记录使用的规则版本。未来若方案修改，新规则只影响指定日期后的事件，历史结果仍可按原版本复算。

## 赛程与内容模型

赛程、规则、通知和奖励数据与页面表现分离：

- 页面组件负责布局，不写死具体日期和队名。
- 赛程数据表达计划、改期、取消、进行中和结束。
- 通知可以关联一个或多个比赛日。
- 所有时间显式保存 `Asia/Singapore` 或赛事最终指定的时区。
- 未确认内容使用明确的 `待公布` 状态，不使用看似真实的占位日期或名单。

## Git 工作流

每项工作遵循以下顺序：

1. 开始前确认工作树状态并识别用户已有修改。
2. 只在对应的新工作区中编辑。
3. 运行格式、类型、数据契约、测试和构建检查。
4. 检查暂存差异，确认没有访问凭据、无关产物或被意外放入 `src`、`public` 的内部数据。
5. 使用详细中文标题与正文提交。
6. 再次确认工作树干净。

提交按可独立回退的逻辑拆分，例如：需求基线、数据契约、页面骨架、视觉系统、积分导出、部署配置分别提交。

## 构建与部署

流水线按顺序执行：

1. 安装 lockfile 固定的依赖。
2. 校验公开数据和内容结构。
3. 扫描网站输入和构建产物中的禁止字段、禁止扩展名和意外大文件。
4. 运行格式、类型和单元测试。
5. 构建静态网站。
6. 运行内部链接、HTML、无障碍和核心页面冒烟检查。
7. 上传并部署 GitHub Pages 构建产物。

`main` 分支通过 GitHub Actions 直接发布到已经绑定的 `scdoudizhu.com`。每次推送后都在线检查首页、积分榜、规则、地图下载、404、HTTPS 与移动端，再根据实际访问反馈继续迭代。旧线上版本保留在 Git 历史中，可以回退到部署前提交。

## 源码与网站构建边界

以下资料允许保存在 `data-source` 或 `references`，但自动拒绝进入 `src`、`public` 或最终 `dist`：

- `.rep`、原始解析 ZIP 和未知二进制数据包。
- 包含 `slotId`、`playerId`、房间 ID、别名等不面向普通访客字段的 JSON/CSV。
- 报名表、别名表、纠错备注和审核记录。
- 未经登记或授权的头像、人物照片和第三方装饰图。

`.env`、访问令牌、账号凭据、私钥等真正的访问秘密在任何目录都不得提交。数据导出脚本只把网站实际需要的字段写入 `src/data`，页面不提供胜负、胜率、单局流水或底层标识的展示和查询入口。
