## 3. 输入契约与必须检查的项目

### 3.1 文件职责和完整性

```text
match-data/
  same_name.csv
  YYYYMMDD/
    YYYYMMDD.json
    HHMMSS,地图名称.rep
    ...
```

生成器读取所有八位日期目录并从首日全量重算，**不会仅追加本次数据，也不会用既有总数据代替缺失的历史原始 JSON**。每个日期目录必须有同名 JSON。若历史输入缺失，先恢复已知本地备份或向用户说明缺失文件；不要删掉已发布历史来迁就当前输入。

本次每条 `fileName` 应在对应目录中有录像，且不存在重复记录；目录多出的录像需要确认是否漏计、备用录像或不计分对局，不要自行全部纳入。处理多份同局录像时防止重复计分。

JSON 顶层是数组，首项是工作人员元数据，其余项是一盘一项。当前契约：

```typescript
// 结构说明，不是可用于发布的示例成绩。
type Metadata = {
  host: string[];
  streamer: string[];
  statistician: string;
  note?: string;
};
type Game = {
  fileName: string; // HHMMSS,地图名称.rep
  duration: string; // 与 durationSeconds 一致的时分秒表达
  durationSeconds: number; // 正整数
  teams: {
    team: 1 | 2 | 3;
    winner: boolean;
    players: {
      name: string;
      race: "Terran" | "Zerg" | "Protoss";
      exitEvent?: number | "掉线";
    }[];
  }[];
};
// 文件内容：[Metadata, ...Game[]]
```

逐项检查，不要认为生成器或 `validate:data` 已覆盖所有输入约束：

- 顶层只有首项是元数据，至少一盘，工作人员字段齐全且类型正确。未开播可为 `streamer: []`；字段缺失或未知工作人员身份不能凭前一日补写。
- 每盘参赛者共 8 人；姓名非空，原始 ID 和归并后的主名称都不应在同盘重复。归并后同盘撞名属于待核实冲突。
- 3v5 为 team 1 的 3 名地主、team 2 的 1 名富农、team 3 的 4 名贫农；2v6 为 team 1 的 2 名地主、team 2 的 6 名农民。遇到新模式先核实支持情况。
- 每盘地主队与农民阵营胜负相反；3v5 的 team 2、team 3 胜负相同；`winner` 必须是布尔值，不能用字符串或推测填充。
- `duration` 与 `durationSeconds` 一致；文件名时间为有效的六位时分秒。生成器依文件名排序，JSON 原来正序或倒序均可。
- `exitEvent` 的数字是普通退出事件序号，**不是扣分标记**；只有字符串 `"掉线"` 进入掉线计分。缺省代表未记录退出事件，不能擅自补成掉线。

### 3.2 录像核对与赛果边界

用户提供的 JSON 是管理员确认的赛果来源。录像核对重点是文件一一对应、人数、姓名、队伍、种族、时长、掉线及退出事件。可用仓库现有 `rep-parser` 或本机已有兼容 screp 解析器检查，不必每次重写解析工具或逐局观看全程。

可用解析器路径要先检查，不能假定另一台机器存在 `D:\screp-main\_release\screp-investigate.exe`。有工具时批量比较本次录像；没有时仍完成 JSON 结构和计分核对，并准确报告尚未做录像独立核验。不要把“JSON 能读取”说成“录像已验证”。录像损坏或与 JSON 有实质冲突时，保留现场，先解决冲突再发布受影响结果。

录像的自动推导胜方或最后退出者不是可靠的 UMS 赛果裁定。不得只因为解析器推测不同就覆盖用户已确认的 `winner`。

KK 录像可能含平台私有槽位或非时间戳随机种子。显示为 1970 年附近的头部时间不等于比赛日期错误；不要把文件名日期写回随机种子，不要原地修复或覆盖原录像。确需修复时使用独立输出，先读现有修复文档和脚本（如存在）。网站显示的 `time` 来自文件名前六位，可能是保存或结束时间，不能擅自改称真实开局时间。

### 3.3 姓名归并

读取完整 `same_name.csv`。每行第一个非空名称是主名称，其余名称归并到它。允许空白、尾部逗号和 UTF-8 BOM；名称按现有生成器精确匹配，区分大小写，不做模糊匹配或自行转小写。

- 同一别名不能分配给多个主名称；只有用户明确提供的关系才可归并。相似昵称也可能是不同的人。
- 原始 JSON 保留原始玩家 ID，由生成器生成 `sourceName` 和 `displayName`，不要为更新显示名而批量改写原始 JSON。
- 比较旧总数据的 `identityGroups` 和新 CSV，列出新增、删除及改动关系。它们可能影响所有历史比赛日、累计场次、胜率、当日唯一人数、工作积分封顶和按周掉线次数。
- 同一人的房主、主播、统计身份先归并，再按当晚封顶计算；不能把两个昵称的已生成总积分机械相加。
- 历史例子：`beinan → do''do` 将 2026-09-07 两盘各 2 分归并后，当日参赛人数减少 1；这不是少计了一名真实选手。

## 4. 当前计分、排名与公开规则

以生成器和掉线配置的实际实现为准，当前基准如下。

| 项目                  | 当前规则                                                                         |
| --------------------- | -------------------------------------------------------------------------------- |
| 地主                  | 胜 12 分、负 3 分                                                                |
| 富农、贫农及 2v6 农民 | 胜 8 分、负 2 分                                                                 |
| 房主、主播、统计员    | 每人当晚分别 10、10、5 分；同一人全部工作积分合计最多 15 分                      |
| 第一次掉线            | 同一主名称、同一赛区、同一周首次：该盘 0 分                                      |
| 第二次掉线            | 该盘为 −15 分，可为负总分，并禁止当周该赛区之后的比赛；不是正常积分再减 15       |
| 周期和赛区            | UTC+8 周一至周日；KK 与韩服分别计数；下周重置                                    |
| 特殊日期              | 仅执行 `excludedMatchdays` 已明确批准的例外，不自行扩大到其他日期                |
| 其他同局玩家          | 按原始赛果正常计分，不因有人掉线整局作废                                         |
| 掉线者统计            | 仍计 1 次参赛与失利，不计获胜                                                    |
| 排名                  | 总分降序；同分按 `displayName.localeCompare(..., "zh-CN")`，不增设胜率或场次决胜 |
| 段位                  | 第 1 王者，第 2–5 星耀，第 6–15 钻石，第 16–25 铂金                              |
| 公开榜单              | 只列前 25 名；当前前 5 名额外含总场数和总胜率                                    |

2026-09-04 的平台故障掉线为已批准例外：该盘 0 分，不计次数、不消耗豁免、不扣分、不触发禁赛。不要恢复旧版“掉线 −20”规则，也不要把任何未来异常自行视为平台豁免。

生成器根据日期推导赛区：周一、周五 KK；周三、周六韩服。其他日期或临时换赛区无法仅靠现有原始 JSON 表达；需有明确赛事安排，再实现相应支持，不能篡改目录日期绕过报错。

公开边界要区分页面：**积分榜不展示单局胜负，赛报会展示逐盘赛果和每日增分**。不要因这两种用途不同而删除赛报赛果，或擅自把完整管理榜放到网站。

## 5. 更新与生成

四份输出只能由 `pnpm run build:match-reports` 生成，不直接手改：

| 输出文件                              | 发布范围                                             |
| ------------------------------------- | ---------------------------------------------------- |
| `data-source/dsl2/dsl2-master.json`   | 本地规范化完整数据，包括原始名称、逐盘积分、完整榜单 |
| `data-source/dsl2/full-standings.csv` | 本地完整管理积分榜                                   |
| `src/data/match-reports.json`         | 公开全部比赛日赛报                                   |
| `src/data/public-standings.json`      | 公开累计积分榜                                       |

原始 JSON 和姓名映射是修正入口；总数据是规范化下游来源，不能通过手改总数据反推纠正上游。

1. 确认本次确有新增比赛、来源修正或待修复生成差异。若来源与全部结果本就一致，不要为了制造提交反复改变发布时间。
2. 当前生成器内 `publishedAt` 是固定字符串。正式刷新数据时，将其设为本次实际发布时间，格式 `YYYY-MM-DDTHH:mm:ss+08:00`；可用带明确 `+08:00` 时区的系统时间获取。不要照抄本文日期，不要把“现在”放进每次运行都会变动的代码，否则 `--check` 无法稳定比较。
3. `standingsAsOf` 由最后比赛日期与最后录像的文件名时间自动生成；它与发布时间不同，不要手改成更新网站的时刻。
4. 执行生成，然后检查一致性；任一步失败必须处理，不能继续提交或发布：

```powershell
pnpm run build:match-reports
if ($LASTEXITCODE -ne 0) { throw '比赛数据生成失败' }
pnpm run check:match-reports
if ($LASTEXITCODE -ne 0) { throw '四份生成数据与来源不一致' }
git diff --stat
git diff -- src/data/match-reports.json src/data/public-standings.json scripts/build-match-reports.mjs
```

更新前运行 `check:match-reports` 因新来源尚未生成而失败是预期现象；更新后失败则不能发布。**`pnpm verify` 不包含 `check:match-reports`，必须单独执行。** CI 没有被忽略的原始资料，所以不能用 CI 成功代替本地来源一致性检查。

页面由 JSON 自动生成：新增比赛日一般无需手工添加新闻、改首页模板或新建逐日 Astro 页面。不要运行第一届预览榜生成命令 `build:preview-standings`，它不属于正式比赛日发布流程。

## 6. 独立复核生成结果

生成器重跑成功不等于输入正确。根据原始 JSON 和最新姓名关系独立核算本次比赛及受身份归并影响的历史记录，不要直接把生成结果当成“期望值”。简单新增日可核对本日与累计差额；涉及历史修正、归并或掉线规则时重算全部受影响日期，必要时全赛季独立核算。

- 本日盘数、归并后实际参赛人数、地主胜盘数与农民胜盘数正确，双方胜盘合计等于总盘数。
- 每个选手当日 `total = matchPoints + workPoints`；工作人员可能未参赛，因此每日积分表行数不必等于参赛人数。
- 核对全部掉线事件的主名称、日期、赛区、周起点、本周序号、豁免或扣分；前一周或另一赛区不得误消耗本周豁免。
- 累计总分等于全部日增分之和，参赛盘数等于胜加负，角色盘数和胜率分母正确；未参赛人员胜率应为 `null`，不能除零。
- 汇总的全体参赛盘数应等于总对局数乘以 8。姓名归并不会减少参赛人次，只会减少唯一身份数。
- 比较发布前后榜单：说明积分、名次、前 25 边界及前 5 统计变化；出现大面积意外变化时先定位来源。
- 纯新增比赛日且映射与历史输入未变时，既有日赛报应保持一致；姓名映射或历史更正则允许相应历史赛报变化，但要能逐项解释。
- 旧日期仍完整保留，日期范围、最新赛报序号、最新统计时间正确。不要将当前“9 日、66 盘”等旧值固化为未来期望。

## 7. 更新验收断言并执行检查

`tests/site.spec.ts` 目前有固定日期、比赛日数量、排名、分数、总场数、胜率、人员行数等断言。每次新增比赛日必须检查它们，否则生成正确也可能在 CI 失败。

先定位：

```powershell
rg -n '比赛日|统计截至|data-rank|总场数|胜率|announcements/20|news-20|toHaveCount' tests/site.spec.ts
```

需要更新的最新状态包括：测试标题、累计第几比赛日、最新日期及时间线锚点、新闻卡片数量、当前榜单、前五场次与胜率。时间线通常还含一个置顶方案，数量比比赛日多 1。新增当日赛报断言，应覆盖盘数、人员数、工作人员、关键增分和发生的掉线事件。

保留有意义的历史回归：2026-08-24 叉子别主播加分、2026-09-04 平台例外、2v6 角色、历史身份归并等。**不要全文件替换日期或数值，不要删断言、扩大容差或复制当前输出以掩盖错误。** 当前榜单中的旧名次断言应随真实累计排名调整；指定历史赛报中的正确断言继续保留。

已有依赖可用则直接运行，不必每次重装。缺依赖时按 `package.json` 的 Node/pnpm 要求运行 `pnpm install --frozen-lockfile`；例行数据更新不升级依赖或改锁文件。

仅对本次修改的代码或测试执行 Prettier，避免 `pnpm format` 全仓改写。随后：

```powershell
pnpm run check:match-reports
if ($LASTEXITCODE -ne 0) { throw '来源一致性检查失败' }
pnpm run verify
if ($LASTEXITCODE -ne 0) { throw '数据、计分、类型、格式或构建检查失败' }
pnpm run test:e2e
if ($LASTEXITCODE -ne 0) { throw '桌面或移动端浏览器验收失败' }
git diff --check
if ($LASTEXITCODE -ne 0) { throw '补丁空白检查失败' }
```

浏览器未安装时可运行 `pnpm exec playwright install chromium`。Windows 已有 Edge 时也可将 `PLAYWRIGHT_EXECUTABLE_PATH` 设为经检查存在的 Edge 可执行文件。端口 4321 被占用时查明进程，不得任意终止其他任务服务或复用旧站点造成假通过。

修复失败项后重跑受影响检查；代码和数据未再变化且检查已通过时不必反复运行整套测试。临时审计脚本、截图及解析产物放 `.audit-tmp/`，不要放进 `src` 或 `public`。

## 8. 提交、推送与等待部署

本地原始录像、`match-data/`、`rep-parser/`、两份完整管理输出、`dist/` 被 Git 忽略是既定设计。**不要 `git add -f` 上传这些资料，也不要修改忽略规则来伪造本地与远端同步。** 正式发布只需要公开生成结果及必要代码、测试和说明。

检查暂存差异后，按明确文件路径暂存本次修改，不使用 `git add .` 或 `git add -A` 混入其他任务文件。例如常规比赛更新为：

```powershell
git add scripts/build-match-reports.mjs src/data/match-reports.json src/data/public-standings.json tests/site.spec.ts
if ($LASTEXITCODE -ne 0) { throw '暂存失败' }
git diff --cached --stat
git diff --cached
```

如有本次新增审计说明或必要逻辑修复，审阅后单独加入。提交用中文，写清比赛日期、数据范围、归并或更正原因及实际验证结果。复杂正文优先写临时 UTF-8 文件并使用 `git commit -F <文件>`，避免 shell 引号破坏玩家名称。提交成功后再执行 `git push origin main`；每步检查退出码。

如推送被拒绝，先 fetch 并理解远端新增提交，保留双方修改后重新验证，不强推。已有用户授权覆盖正常的冲突整合；无法裁定的数据冲突需明确提出具体问题。

推送到 `main` 自动触发 `.github/workflows/pages.yml`，无需另配部署服务。使用本次提交 SHA 匹配运行，不要拿上一次成功结果当本次发布成功：

```powershell
git rev-parse HEAD
gh run list --workflow pages.yml --limit 5 --json databaseId,headSha,status,conclusion,url
# 根据 headSha 选出本次运行 ID，再执行：
# gh run watch <本次运行ID> --exit-status --interval 15
```

Actions 会再次执行 `pnpm verify`、桌面与移动端测试、上传静态产物、部署 GitHub Pages。必须等待 build 和 deploy 都成功。长耗时工具采用可恢复会话，保持简短进展更新；不要每秒轮询。失败时读对应运行日志，修复后新增提交重新发布，不报告成功。

最终检查本次提交已在远端，当前输入与四份输出一致，本次没有遗漏修改。原先存在的其他任务文件仍然保留。

## 10. 异常处理与交付格式

### 可以自主完成

确定来源后重新生成陈旧输出、更新已过期的最新状态断言、修正本次格式、安装缺失的已声明依赖或浏览器、处理可明确判断的代码问题、在授权范围内提交和发布。不要为这些常规步骤重复向用户确认。

### 需要明确事实或赛事裁定

缺失历史 JSON 或本次关键输入、工作人员身份未知、JSON 与录像实质不符、别名冲突、同一归并身份在同盘出现两次、胜方互相矛盾、禁赛期间继续出场、未支持的模式或临时赛区安排。先完成不依赖该信息的检查，保留原数据，说明具体文件、对局和冲突；只询问解决问题必需的信息。不得编造、删盘、改日期、改掉线标记或关闭禁赛检查来让流程通过。

生成器可能在中途失败前已写入部分输出，失败后不要发布半更新结果；处理来源后完整重跑，必要时与本次备份核对。

### 最终回答必须包含

1. 已完成到哪一步：仅本地、已推送、已部署并在线核验，按事实写。
2. 更新的比赛日期、当日盘数与人数、累计比赛日及盘数。
3. 发现并修正的问题；姓名归并、掉线、工作积分、关键排名变化，无则明确未发现。
4. 本地总数据和完整积分榜路径，以及可选的详细审计记录路径。
5. 实际通过的检查、浏览器测试数量、线上核验结果，不复制历史测试数量。
6. 提交 SHA、对应 Actions 链接、正式积分榜和本次赛报链接。
7. 未完成事项或保留的其他任务文件，仅在存在时简要说明。

不要以“已经推送，等部署即可”作为完成；不要在没有查看线上页面时宣称本地与线上一致。
